# V1.9.17 — Automatic library and channel restoration

## Root cause
The previous startup path ran two independent flows: `DOMContentLoaded` called `loadCountry()` while `bootFromServer()` separately loaded the shared library. These asynchronous flows could finish in either order, so the country list could overwrite the library. In addition, `setPower(true)` played the default channel before restoration and could update last-channel/history state.

## Changes
1. Removed the competing `loadCountry()` call from initial DOM setup.
2. Unified startup through a single-flight `bootFromServer()` promise.
3. On startup, read library stats; if the shared library contains channels, fetch user state and automatically load the library. Otherwise load the selected built-in country list.
4. Keep playback off during restoration, then power on only after the channel list and saved state have been resolved.
5. Restore the last channel by ID from server state, falling back to the browser's saved channel ID.
6. Validate HTTP status and API response shape before replacing the channel list.
7. Prefer the browser-saved channel ID during automatic boot when server state has no last channel.
8. Bumped the service-worker cache key so updated JavaScript is fetched after deployment.
9. Added regression tests for the startup ordering and automatic library restore path.

## Preserved
Player/HLS engine, channel source definitions, import flow, security modules, AI and Feedback modules, bilingual language system, and UI layout are unchanged.

## Validation
- `node --check public/app.js`
- `node --check server.js`
- `npm test`
- ZIP integrity check
- Static regression assertions for single startup flow, automatic library loading, and delayed power-on.

## Limitations
A live browser/Docker end-to-end run depends on the target SoloHost environment and actual imported channel data. Library entries must still contain playable source URLs; expired or restricted streams cannot be made available by memory restoration alone.
